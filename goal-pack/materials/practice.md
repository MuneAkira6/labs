# 実務の記録（labs の一次資料）

このファイルは、筆者が実務で扱った三つの小さな成果について、このリポジトリで書いてよいことのすべてです。
README とスクリプトの中で実務に触れる文は、ここに書かれていることだけに基づきます。実務の数値はここにも
README にも書きません。数値は事例集の[事例 07](https://github.com/MuneAkira6/engineering-case-studies/blob/main/07-other-work.md)
にだけあり、README からはそこを指します。製品名・会社名・人名・チケット番号も書きません。

## 1. A：レポートの N+1 を一括読み出しに

- 対象は、利用者別のレポート 4 種類でした（利用者別 / グループ別 × 利用量 / 課金）。
- もとの実装は、グループごと・利用者ごとに 1 回ずつデータベースを読み、しかもそのたびに完了をブロックして
  待っていました。件数が増えると、読み出しの回数が利用者の数に比例して増えます。
- 直し方は三段でした。互いに独立したクエリを先にまとめて発行する。利用者単位の集計を 1 回だけ行う。
  メモリ上で、もとの出力と同じ順序に畳み込む。
- 速さより先に、「振る舞いが変わっていないこと」の証明を決めました。
  - 旧実装の出力を最初の goal で一度だけ採取して金型にし、その後は変更を禁じる。
  - 採取の前に、同じ旧実装を続けて流して出力が一致する（決定的である）ことを確かめる（A/A）。
  - CSV は生のバイト列（BOM を含む）で比べる。並べ替えや正規化をしてから比べることはしない。
  - データベースへの要求は、1 回の出力の分だけを数える。ほかの処理が混ざっていないかを見張る。
- 実装と計測は、長命バス方式で無人で回しました。
- 数字は、機械に依存しない量（要求の回数）と、機械に依存する量（時間）を分けて示しました。

## 2. B：専用スレッドプールのデッドロック

- 症状は、一部の処理だけが応答しなくなり、ほかの処理は普通に速く返る、というものでした。
- 原因は、最大 3 スレッドの専用プールの上で、ある処理が別の処理の完了を無期限にブロッキング待機していた
  ことです。待たれている側の処理も、同じプールで動く必要がありました。同時に 3 件来るとスレッドがすべて
  待機で埋まり、待たれている処理が永久に実行されません。
- 直し方は、プールの大きさを変えずに、ブロッキング待機をすべて非同期処理（Future）の合成に置き換える
  ことでした。
- 確かめ方は、間隔をおいた 3 回のバースト（最大 20 並列）でした。すべての要求が成功し、バーストの後の
  単発の要求も成功して、プールが生きていることを示しました。
- 別の件では、「待機が二つ重なれば必ず凍る」という自分の仮説を、小さな Scala のコード片で反証しました。
  共有の ForkJoin プールは、ブロッキングを検知すると補償のスレッドを足すので、既定の設定では凍りません。
  仮説を確かめるときは、手元で再現できる小さなコードで反証しにいく、という順序を守りました。

## 3. C：webpack + Babel から Rsbuild へ

- 管理画面のビルドを、webpack + Babel から Rsbuild（SWC）に移しました。三つあった webpack の設定と
  Babel を、Rsbuild の設定一つにまとめています。
- React のバージョンの都合で、JSX は classic runtime（`React.createElement`）のままにしました。
- 移行の前に、パッケージマネージャーを npm から pnpm に移しています。
- 移行で当たった互換の問題は、出力ディレクトリの構成、生成される HTML のファイル名、多言語リソース生成の
  組み込み、フォント配信のルーティング、一部ライブラリの別名設定でした。
- 移行後の本番ビルドの時間は、開発者の端末で 1 回だけ測りました。移行前の時間は記録を残していなかった
  ため、実務の記録だけでは前後を比べられません。
